# SCI0 resource round-trips

## Layers and API

`scimate_core` is standard C++17 and performs no filesystem or UI operations:

- `decode_sci0(method, bytes, expected_size)` decodes one bounded payload.
- `read_sci0_game(GameFiles)` validates the map, referenced volume headers and
  payloads, and returns ordered resources plus original files.
- `rebuild_sci0_game(Game)` accepts payload edits and returns verified map and
  volume bytes. Metadata edits and additions/deletions are rejected.

`scimate_application` owns filesystem operations: `open_sci0_game`,
`export_sci0_game`, and `import_sci0_game`. The CLI calls these operations.
No library depends on Qt, Windows APIs, or the legacy repository.

## Volume format and validation

A resource begins at its map offset with four little-endian 16-bit words:
packed type/number, stored length, decoded length, compression method. Stored
length includes the final four header bytes; the full record length is stored
length plus four. IDs must match the map. Stored length must be at least four;
the full header and payload must fit in the referenced volume. Zero-length
stored payloads are supported when the decoded length is also zero.

Methods: 0 = stored, 1 = SCI0 LSB-first LZW (9..12 bits), 2 = SCI Huffman.
LZW/Huffman require a complete end marker and exactly the declared decoded
length. Backreferences, node offsets, bit reads, and output writes are bounded.
Unused bits/bytes after a compressed end marker are allowed and preserved in
unchanged records. These are strict decoders: a legacy stream accepted only
because an older decoder ignored truncation may be rejected. Unknown methods
fail explicitly. SCI1 compression dispatch is different and is unsupported.

Repeated IDs and repeated references to the same record are allowed. No active
version is selected, and no resource is silently discarded. Volume loading does
not require `resource.000`; only volumes referenced by the map are read.

## Export format, version 1

```text
manifest.tsv
original/resource.map
original/resource.NNN        # one per referenced volume
payloads/0000000.bin         # map ordinal, not resource number
payloads/0000001.bin
scripts/0000000.asm          # if this ordinal is a supported script
scripts/0000001.error.txt    # if this script cannot be disassembled
...
```

`manifest.tsv` uses LF newlines, with a `SCIMATE-SCI0-EXPORT<TAB>1` first line.
The next line names these columns: index, type (numeric), number, volume,
offset, compression, decoded_size, file. All metadata describes the original
game, including the original decoded size even after a payload edit. The
importer regenerates and compares the canonical manifest to the snapshots;
it does not interpret user-provided paths or accept changes to metadata.
Do not change the manifest, its line endings, or files under `original/`.

Every expected payload file must exist. Unlisted extra files are ignored and
do not add resources. Import/export is an internal interchange format, not
SCI Companion's standalone resource/patch format. Regular input files are
required; symlinked files are rejected.

Script inspection sidecars and their failure behavior are described in
[human-readable script export](sci0-scripts.md). Import ignores these sidecars;
only binary payload edits affect reconstruction.

## Guarantees

With unchanged payloads, the map and all referenced volumes are returned
byte-for-byte, including compressed bytes, gaps, aliases, and trailing data.
Unreferenced volumes and non-resource game files are outside this guarantee.

With edits, volumes are rebuilt in map order with new offsets. Each unchanged
resource keeps its original header and compressed record. Each changed
resource gets a new header and uncompressed payload. Resource order, IDs,
duplicates, and volume assignments are preserved. Gaps and unused records may
be discarded; aliased records may become separate copies.

The core reopens the generated byte buffers and compares decoded payloads. The
application then writes into a new directory, reopens it through the same
reader, and compares saved map/volume bytes. Synthetic known-output codec tests
provide a separate check beyond writer/reader self-consistency. This is not
validation by Sierra's interpreter, ScummVM, or the Windows editor.

## Limits and failure behavior

- SCI0 header limits: at most 65,535 decoded bytes; at most 65,531 stored bytes.
  Modified resources are stored uncompressed, so edits are limited to 65,531
  bytes even if the original compressed resource decoded to a larger size.
- Map offsets are limited to 26 bits and volume numbers to 0..63.
- Defensive allocation limits: map 16 MiB, total input files 256 MiB, total
  decoded payloads 256 MiB, and rebuilt files 256 MiB. Operations may hold
  multiple copies while validating; these limits are not peak-memory bounds.
- Existing destinations are always refused. Their parent directories must
  already exist. Inputs are read-only. Malformed inputs are rejected before
  creating the output directory.
- Directory writes are not transactional. An I/O failure or interrupted process
  can leave partial output, which must be removed or given a new destination
  before retrying. Export writes its manifest last; reconstruction writes its
  map last. Originals remain untouched.

Payload content is opaque. The tools validate storage structure and decoding,
not scripts, view structures, text encodings, or gameplay correctness.
